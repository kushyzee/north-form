## 1. Project Overview

**Name:** `north-form` — NORTH & FORM, a **fictional** Nigerian men's fashion brand.
Tagline: *"Built for the way you move."*

**Purpose:** A storefront where a visitor browses a Supabase-backed catalogue, adds pieces to a
browser-local cart, signs in with Google, and places an order. The architectural centre of the
project is that **the database computes and validates the order** — the browser contributes only
intent (which product, how many, which size) plus typed contact/delivery text. Everything monetary,
identity-related, and status-related is derived server-side by a `SECURITY DEFINER` Postgres function.

**User types / roles:**

| Role | Exists? | How enforced |
|---|---|---|
| Anonymous visitor | Yes | Default. May browse `/`, `/shop`, `/shop/[slug]`, `/cart`. |
| Authenticated customer | Yes | Supabase Auth (Google only). RLS scopes their rows via `auth.uid()`. |
| Admin | **No** | No admin role, route, UI, or `is_admin` column. Orders are never advanced past `awaiting_payment` by any code path. |

**Core user journeys implemented:**

1. Browse -> filter/search/sort -> product detail -> select size/quantity -> add to bag
2. Bag -> adjust quantities -> remove -> clear
3. `/cart` -> `/checkout` -> auth guard redirects to `/auth` -> Google OAuth -> back to checkout
4. Fill checkout form -> `POST /api/orders` -> DB creates order -> redirect to confirmation page
5. Order confirmation page renders from DB; confirmation email sent to the **verified** account address

**Deliberately not built:** payment verification/webhook, stock decrement or reservation, order
history/list, admin functionality, catalogue management, profile persistence on checkout, discounts.

**Architecture in short:** Next.js App Router. Server Components read Postgres directly through a
per-request Supabase server client. All client<->server writes go through one Route Handler. The only
database write path to orders is a Postgres function in a non-exposed `private` schema. `proxy.ts`
(Next 16's replacement for `middleware.ts`) refreshes the Supabase session on every request.

## 5. Data Model

Schema lives in `supabase/migrations/`; it is **applied and live**. Source of truth is the
migrations, not the dashboard.

### `public.profiles`

| Column | Type | Notes |
|---|---|---|
| `id` | `uuid` **PK** | `-> auth.users(id) ON DELETE CASCADE` |
| `full_name` | `text NOT NULL` | |
| `email` | `text NOT NULL` | Convenience copy; `auth.users` is authoritative |
| `phone` | `text` | nullable — Google does not supply one |
| `created_at` / `updated_at` | `timestamptz` | `updated_at` maintained by trigger |

Created **only** by the `on_auth_user_created` trigger (`security definer`, `search_path = ''`).
There is deliberately **no INSERT policy**.

### `public.categories`

`id uuid PK default gen_random_uuid()`, `name text NOT NULL CHECK (btrim <> '')`,
`slug text NOT NULL UNIQUE CHECK (slug ~ '^[a-z0-9]+(-[a-z0-9]+)*$')`, `description text`,
`created_at`. Seeded with 4: `shirts`, `jeans`, `shoes`, `hoodies`.

### `public.products`

`id uuid PK`, `category_id uuid NOT NULL -> categories(id) ON DELETE RESTRICT`, `name`,
`slug UNIQUE` (same regex check), `description`,
**`price numeric(12,2) NOT NULL CHECK (price >= 0)`**,
**`stock_quantity integer NOT NULL DEFAULT 0 CHECK (>= 0)`**,
**`sizes text[] NOT NULL DEFAULT '{}'`**, **`images text[] NOT NULL DEFAULT '{}'`**,
`featured boolean NOT NULL DEFAULT false`, `created_at`, `updated_at`.

Indexes: `products_category_id_idx`, partial `products_featured_idx WHERE featured`.

Seeded with 12 fictional products. Featured: Essential Oxford N28,000 · Baggy Jeans N35,000 ·
Classic Court Sneaker N55,000 · Studio Heavyweight Hoodie N45,000. Prices span N22,000–N62,000,
stock 10–40 units. Sizes: apparel `S–XXL`, jeans `30–38`, shoes `40–45` (Everyday Slide `39–45`).
Every product has exactly 2 images, so the gallery thumbnail strip always renders.

### `public.order_status` (enum)

`awaiting_payment` | `payment_confirmed` | `processing` | `shipped` | `delivered` | `cancelled`.

Adding a value later requires **its own migration** (`ALTER TYPE ... ADD VALUE`) — a value added
in a transaction cannot be used by that same transaction.

### `public.orders`

`id uuid PK`,
**`user_id uuid -> auth.users(id) ON DELETE SET NULL` (nullable — deleting an account must not destroy order history)**,
`order_number text NOT NULL UNIQUE`,
`status order_status NOT NULL DEFAULT 'awaiting_payment'`,
`customer_name/email/phone/delivery_address/delivery_city/delivery_state text NOT NULL`
(all with `btrim <> ''` checks),
**`subtotal`, `delivery_fee`, `total` all `numeric(12,2) NOT NULL CHECK (>= 0)`**, plus the
table-level constraint:

```sql
constraint orders_total_matches_subtotal_delivery check (total = subtotal + delivery_fee)
```

Index: `orders_user_id_created_at_idx (user_id, created_at desc)`.

### `public.order_items`

`id uuid PK`, `order_id uuid NOT NULL -> orders(id) ON DELETE CASCADE`,
**`product_id uuid NOT NULL -> products(id) ON DELETE RESTRICT`**,
**`product_name text NOT NULL`** (historical snapshot),
`quantity integer NOT NULL CHECK (quantity > 0)`, `size text NOT NULL CHECK (btrim <> '')`,
**`unit_price numeric(12,2) NOT NULL`** (historical snapshot), `created_at`.

Indexes: `order_items_order_id_idx`, `order_items_product_id_idx`.

### `private` schema (not a table)

Created by `20261001181519_create_place_order_function.sql`. Holds `place_order(...)`. Exposed to
PostgREST via `alter role authenticator set pgrst.db_schemas = 'public, graphql_public, private'`.

### Relationships

```
auth.users ---1:1---> profiles (CASCADE on delete)
auth.users ---1:N---> orders.user_id               (SET NULL - history preserved)
orders      ---1:N---> order_items                 (CASCADE)
products    ---1:N---> order_items                 (RESTRICT - sold products can't vanish)
categories  ---1:N---> products                    (RESTRICT - never orphan a product)
```

**Conceptually:** `User -> Orders -> Order Items -> Products -> Categories`.

### `private.place_order()` — the only order write path

```sql
private.place_order(
  p_cart jsonb,                 -- [{"product_id": uuid, "quantity": int, "size": text}]
  p_customer_name text, p_customer_email text, p_customer_phone text,
  p_delivery_address text, p_delivery_city text, p_delivery_state text
) returns jsonb                 -- {order_id, order_number, subtotal, delivery_fee, total}
```

`SECURITY DEFINER`, owned by `postgres`, `set search_path = ''`, every table fully qualified.
**There are no `p_user_id`, `p_unit_price`, `p_subtotal`, `p_delivery_fee`, `p_total`, `p_status`
or `p_order_number` parameters** — the function has no way to receive a forged value for any of them.

It performs, in order: `auth.uid()` non-null check -> blank/length checks on all text ->
36-states+FCT membership -> cart is a JSON array and non-empty -> per-item key presence/type/regex
checks (UUID, non-blank size, numeric `quantity` matching `^[0-9]{1,6}$` and `>= 1`) -> duplicate
`(product_id, size)` rejection -> one SQL pass computing missing/size-mismatch/stock counts **and**
the authoritative subtotal -> fee from `v_state` alone -> order insert with a retry loop around
`unique_violation` -> `order_items` insert joined to `products` (name and price read from the
catalogue) -> JSONB return.

Any failure raises `errcode = 'P0001'` with the machine code as the **message** and human text as
**detail**: `UNAUTHENTICATED`, `INVALID_CUSTOMER`, `INVALID_STATE`, `INVALID_CART`, `EMPTY_CART`,
`INVALID_CART_ITEM`, `PRODUCT_NOT_FOUND`, `INVALID_SIZE`, `INSUFFICIENT_STOCK`,
`ORDER_CREATION_FAILED`.

**Migration history is append-only.** Four migrations each redefine the function to fix one bug:
`= all()` -> `= any()` for size membership (subtotal and stock were silently broken), explicit
`is null` on every JSON key (`jsonb_typeof` of a missing key is SQL `NULL`, and `NULL or NULL` is
`NULL`), and an explicit `quantity >= 1` lower bound. Do **not** edit an already-recorded migration.

## 6. Authentication and Authorization

### Authentication — "Who is this user?"

**Provider: Google only.** No email/password, magic link, phone, or custom OAuth.

```
/auth  ->  GoogleSignInButton (browser client, signInWithOAuth, PKCE)
       ->  Google consent       ->  /auth/callback?code=...&next=...
       ->  exchangeCodeForSession(code) on the SERVER client
       ->  session cookies ride along on NextResponse.redirect
       ->  validated `next`
```

- `components/auth/google-sign-in-button.tsx` builds `redirectTo` from `window.location.origin` —
  no hardcoded host, one code path for localhost/preview/production.
- `app/auth/callback/route.ts` reads/writes **no cookies by hand**. It calls
  `exchangeCodeForSession` and lets Supabase's cookies ride on the redirect response. The browser
  only ever holds httpOnly Supabase cookies; **no access or refresh token reaches client JS**.
- `proxy.ts` -> `lib/supabase/proxy.ts` -> `updateSession()` calls `supabase.auth.getClaims()` on
  every matched request purely to trigger the token refresh. It performs **no route protection**
  (`void data` — the data is deliberately discarded).
- `lib/auth/session.ts` -> `getAuthUser()` returns `{ id: claims.sub, email }` from **verified
  claims**. It deliberately does **not** use `getSession()` (not re-validated). `session_not_found`
  is treated as a normal anonymous state and is not logged.
- `requireAuthUser(nextPath)` = `getAuthUser()` + `redirect('/auth?next=...')`. Used by exactly two
  pages: `app/checkout/page.tsx` and `app/checkout/confirmation/[orderNumber]/page.tsx`.
- Profile creation is the DB's job: `on_auth_user_created` trigger -> `public.handle_new_user()`
  (`security definer`, `on conflict (id) do nothing`).

### Authorization — "Is this user allowed?"

Three independent layers:

**1. Route guard (UI/UX only):** `requireAuthUser()` inside the page body. Protects the *route*,
not any data.

**2. RLS (the actual row boundary):**

| Table | Policy | For | Using |
|---|---|---|---|
| `categories`, `products` | `SELECT` | `anon, authenticated` | `true` |
| `profiles` | `SELECT`, `UPDATE` | `authenticated` | `(select auth.uid()) = id` |
| `orders` | `SELECT` | `authenticated` | `(select auth.uid()) = user_id` |
| `order_items` | `SELECT` | `authenticated` | `exists (select 1 from orders o where o.id = order_items.order_id and o.user_id = (select auth.uid()))` |

**There is no INSERT/UPDATE/DELETE policy on `orders` or `order_items`.** No write policy exists
on `categories` or `products` either. All policies use `(select auth.uid())` for initplan caching.

**3. Grant matrix (ACL layer, defence in depth):**

| Role | Access |
|---|---|
| `anon` | `SELECT` on `categories`, `products` — nothing else |
| `authenticated` | `SELECT` on all five tables; `UPDATE` on `profiles` only |
| `service_role` | `ALL` (bypasses RLS; server-only — **not used by any application code**) |

Supabase's default privileges grant `ALL` (including `TRUNCATE`/`REFERENCES`/`TRIGGER`, which RLS
does not cover), so migrations `20260930220536` and `20260930220757` explicitly restate this matrix.

**On the RPC:** `revoke all on schema private from public, anon, authenticated` ->
`grant usage to authenticator, authenticated` -> `revoke all on function ... from public, anon` ->
`grant execute ... to authenticated`. So `anon` has neither `EXECUTE` nor `USAGE` and PostgREST
answers `42501`.

**Unauthenticated handling:** storefront pages render normally; `/checkout*` redirect (307) to
`/auth?next=...`; `POST /api/orders` answers `401 UNAUTHENTICATED`.

**Open-redirect protection:** `lib/auth/redirect.ts` -> `safeRedirectPath()` accepts only a
single-slash absolute path. Rejects `//evil.example`, `/\evil.example`, control chars
(<= `0x1f`, `0x7f`), then resolves against a throwaway origin as defence in depth. Both `/auth` and
`/auth/callback` funnel through it.

**Security boundaries to preserve:**

- The Route Handler **repeats** authentication rather than inheriting the page guard — a browser
  can call `POST /api/orders` directly.
- `getOrderByNumber()` takes **no user id**. RLS decides what is readable, so another customer's
  order number resolves to nothing -> `notFound()`. The `404` is deliberately indistinguishable
  from "does not exist" to avoid an order-existence oracle.
- There is **no admin role** — do not add one without a full RLS + policy migration.

## 7. Core Feature Flows

### Product browsing

`app/shop/page.tsx` reads `?category=`, `?q=`, `?sort=`, normalises each (`firstParam()` for arrays,
`.trim()`, `isProductSort()` narrowing, category validated against the real slug set) and passes them
to `getProducts()` in `lib/catalogue/queries.ts`.

`getProducts()` builds **one** Supabase query chain: `.eq("category.slug", ...)`,
`.or('name.ilike.%t%,description.ilike.%t%')` (the term is escaped via `toLikePattern()` which
strips `,%().\`), then an order chain with `name` as a stable tiebreaker. **All filtering, search
and sorting happen in Postgres** — never fetch-and-sort in JS.

Every row is validated from `unknown` by `toProduct()`/`toCategory()` into the domain types.
`server-only` is imported; errors are logged and `[]` returned.

### Cart

- **State:** `CartProvider` (`useReducer(cartReducer)`) in React context, hydrated from
  `localStorage` key `north-form:cart:v1`.
- **Line identity:** `${productId}::${size ?? ""}`. Same product + same size merges; different
  sizes stay separate.
- `addItem()` comes from `ProductPurchasePanel`: requires a size when `product.sizes.length > 0`,
  refuses zero stock, passes `unitPrice: product.price` and `maxQuantity: product.stockQuantity` as
  an **add-time snapshot**.
- `clampQuantity(q, max)` floors, returns `1` for NaN/Infinity/`<1`, caps at `max`. `decrement`
  from 1 **removes** the line rather than parking at 0. `maxQuantity <= 0` -> the add is refused.
- `readStoredCart()` treats storage as untrusted: validates each entry, **recomputes** `lineId` from
  its parts, drops invalid entries, and re-clamps `quantity` to `maxQuantity`.
- **Totals:** `getCartCount()`, `getCartSubtotal()` (sum of `unitPrice * quantity`) are pure
  client-side display values.

### Checkout — full trace

**1. What the client collects** (`components/checkout/checkout-form.tsx`): `fullName`, `email`,
`phone`, `address`, `city`, `state`. Pre-filled from `getCheckoutProfile(user.id)` but always
editable; **never written back**. `state` has no default so the enum reports "Select your state."

**2. What is sent to the server** — exactly:

```json
{ "fullName", "email", "phone", "address", "city", "state",
  "cart": [{ "productId": uuid, "quantity": int, "size": string }] }
```

No price. No subtotal. No fee. No total. No status. No user id. No order number.

**3. Server-side validation** (three layers, in order):

- `orderRequestSchema` = `checkoutSchema.extend({ cart }).strict()` — `.strict()` means a forged
  `total`/`userId`/`status`/`orderNumber` is a **400**, not a silent strip. Plus `.refine()`
  rejecting duplicate `productId::size` lines. Cart: 1–50 lines; quantity int 1–999,999;
  `productId` must be a UUID.
- `private.place_order` re-validates everything independently (see section 5).
- Table `CHECK` constraints as the final backstop.

**4. How prices are determined:** `products.price` read inside the function.
`sum(p.price * l.quantity)` filtered to valid lines only.

**5. Inventory:** **validated, never mutated.** `l.quantity > p.stock_quantity` ->
`INSUFFICIENT_STOCK` (HTTP 409). Two customers can both pass the check for the last unit — a
documented deferral, not an oversight.

**6–7. How the order and items are created:** both inside the single function body => **one
transaction**. The whole cart is validated *before* any insert, so one bad line rolls back
everything — there is no partial order. `orders.status` takes the column default
`awaiting_payment`. `order_items.product_name` and `unit_price` are snapshots from `products`.

**8. Payment:** none. No gateway, no webhook, no verification. The order stays `awaiting_payment`
forever unless a human moves it. Bank details are `DEMO_BANK_TRANSFER` in
`lib/orders/payment-details.ts`, shared by the confirmation page and the email so they can never drift.

**9–10. After success/failure:**

- Success (`201`): `clearCart()` -> `setPlaced(true)` (prevents an empty-cart flash) ->
  `router.replace('/checkout/confirmation/<orderNumber>')`. The confirmation page **re-reads the
  order from the DB**; nothing survives the redirect except the order number used to address the row.
- Failure: `readApiError(payload, status)` renders `error.message` in an `aria-live` status region
  with a link back to `/cart`. Network failure shows deliberately ambiguous copy (the order may or
  may not have landed).
- Duplicate submits are blocked by `inFlight` (`useState`, not a ref — React Compiler reasons about
  it) plus `disabled={busy}`. There is **no idempotency key**; a retried POST creates a second order
  and a second email.

### Orders

- **Create:** `POST /api/orders` only (above).
- **Retrieve:** `getOrderByNumber()` in `lib/orders/queries.ts` — selects `orders` + embedded
  `order_items(...)`, validated from `unknown`, returns `null` on error/absence.
- **Display:** `app/checkout/confirmation/[orderNumber]/page.tsx` renders DB totals, status, items
  and address. `isAwaitingPayment(order.status)` selects the wording; **nothing ever says payment
  was received**.
- **Update:** **there is no update path anywhere in the application.** Orders are immutable
  post-creation from the app's perspective.

### Admin functionality

**None.** No admin route, no role check, no admin table, no management UI. `orders` and
`order_items` have no UPDATE/DELETE policy for any client role, so there is currently no
application- or RLS-level path to advance an order's status.

## 8. Data Flow

### Catalogue read (server)

```
URL searchParams -> app/shop/page.tsx (normalise/drop unknown)
  -> getProducts() [server-only] -> createClient() [lib/supabase/server.ts, async cookies()]
  -> PostgREST -> RLS(anon/authenticated SELECT) -> rows validated from unknown -> Product[]
  -> ProductGrid / ProductCard [RSC] -> HTML
```

All routes are **dynamically rendered** because `lib/supabase/server.ts` awaits `cookies()`. A
`revalidate` export would have no effect — several source comments say this explicitly.

### Cart write (client only)

```
ProductPurchasePanel -> addItem(snapshot) -> cartReducer -> CartProvider state
  -> writeStoredCart() -> localStorage["north-form:cart:v1"]
 -> re-read on mount -> readStoredCart() (validated) -> hydrate
```

No server involvement at all.

### Order placement

```
CheckoutForm.onSubmit (RHF -> checkoutSchema)
  -> fetch POST /api/orders {form values, cart lines}
  -> app/api/orders/route.ts
      -> request.text()            (malformed body -> 400, not a SyntaxError)
      -> getAuthUser()             (server session only)
      -> handlePlaceOrder({ rawBody, userId, placeOrder })   <- PURE, unit tested
          -> orderRequestSchema.safeParse
          -> toRpcParams()
          -> placeOrder(params)
 -> createClient().schema("private").rpc("place_order", params)
              -> Postgres: validate -> price -> insert orders + order_items
              -> mapPlacedOrder(data)
          -> mapPlaceOrderError(error) on failure
      -> if 201: notifyOrderPlaced({ recipient: user.email, loadOrder: getOrderByNumber, sendEmail })
          -> sendOrderConfirmationEmail -> buildOrderConfirmationEmail -> sendMailgunMessage -> fetch()
      -> NextResponse.json(result.body, { status })
  -> back in the client: onOrderPlaced(orderNumber)
 -> clearCart() -> setPlaced(true) -> router.replace(/checkout/confirmation/<n>)
      -> Server Component -> requireAuthUser() -> getOrderByNumber() -> render
```

**Key observation:** the API does **not** echo its own totals to the client. It re-reads the order
through the RLS-scoped `getOrderByNumber()` so the email is built from the database (which has the
line items and delivery snapshot), not from the RPC's return value.

### Client-side state summary

There is **no** server-state cache (no SWR/React Query), no `useSWR`, no `revalidatePath`/
`revalidateTag`. Server Components fetch on every request. `router.refresh()` is used once — after
sign-out, so server reads reflect the cleared session immediately.

## 9. Business Logic

| Rule | Enforced where | Server/DB? |
|---|---|---|
| Product price | `products.price`, `numeric(12,2) NOT NULL CHECK (>= 0)`; read inside `place_order` | **DB** |
| Subtotal | `sum(p.price * quantity)` in `place_order`; `orders_total_matches_subtotal_delivery` CHECK | **DB** |
| Delivery fee | `getDeliveryFee()` (display, client) **and** a `CASE` on `v_state` in `place_order` (authoritative). Lagos 2000, FCT 2500, Rivers 3000, else 4000 | **Both, DB authoritative** |
| Total | `subtotal + delivery_fee`, both in the function and enforced by the table CHECK | **DB** |
| Order owner | `auth.uid()` inside `place_order`; `auth.uid() = user_id` in the `orders` RLS policy | **DB** |
| Order number | `'NF-' \|\| upper(substr(uuid hex, 1, 16))` with a 3-try `unique_violation` retry loop | **DB** |
| Initial status | Column default `awaiting_payment`; not a parameter | **DB** |
| Stock sufficiency | `quantity > stock_quantity` -> `INSUFFICIENT_STOCK`; `stock_quantity >= 0` CHECK | **DB** (validated, **never decremented**) |
| Size validity | `size = any (p.sizes)` inside the function | **DB** |
| State validity | `state = z.enum(NIGERIAN_STATES)` (Zod) **and** `v_state <> all (array[...37])` (SQL) | **Both, duplicated on purpose** |
| Cart line uniqueness | `.refine()` in Zod **and** `GROUP BY ... HAVING count(*) > 1` in SQL | **Both** |
| Quantity >= 1 | Zod `.min(1)` **and** regex `^[0-9]{1,6}$` + `>= 1` in SQL **and** `order_items CHECK (quantity > 0)` | **Three layers** |
| Cart line count 1–50 | Zod only (`cartSchema.max(50)`) | **API only** |
| Product availability | `getAvailability()` / `LOW_STOCK_THRESHOLD = 5` — client-side presentation **and text, never colour alone** | **Client only (display)** |
| Cart quantity ceiling | `clampQuantity()` client-side; DB re-checks against live stock | **Both** |
| Order history preservation | `orders.user_id ON DELETE SET NULL`; `order_items.product_id ON DELETE RESTRICT` | **DB** |
| Profile row creation | `on_auth_user_created` trigger only | **DB** |
| Price/total forging | `.strict()` on the request schema + no RPC parameter exists + `SECURITY DEFINER` owns every value | **API + DB** |

**Phone validation** (`lib/checkout/phone.ts`) is about *shape*, not formatting: separators
stripped, then `/^0\d{9,10}$/` or `/^234\d{9,10}$/`.

## 10. Security and Trust Model

### Client-controlled (and how it is treated)

| Client input | Trust level |
|---|---|
| `productId`, `quantity`, `size` per line | Intent only. Validated 3x (Zod, SQL shape, catalogue join). |
| name/email/phone/address/city | Stored as a business snapshot; length-checked in SQL. |
| `state` | Must match the canonical 37-name list in Zod **and** SQL. |
| Order number in the confirmation URL | An *address*, not an authorisation. RLS decides readability. |
| `next` in `?next=` | Untrusted. `safeRedirectPath()` on every use. |
| Everything else | **Rejected by `.strict()`.** |

### Server/database-derived (the client has no way to influence these)

`user_id` (`auth.uid()`), `unit_price` (`products.price`), `product_name` (`products.name`),
`subtotal`, `delivery_fee`, `total`, `status`, `order_number`, `created_at`.

### Protections to preserve when extending

1. **Never add a client INSERT policy on `orders`/`order_items`.** The write boundary is the
   function, not a policy. A permissive policy lets anyone forge prices, totals and user ids.
2. **Never add a `p_user_id` (or price/total/status) parameter to `place_order`.** Its power comes
   from having *no* such parameters.
3. **Never use a service-role key in application code.** `SUPABASE_SECRET_KEY` is documented in
   `AGENTS.md` as deliberately unused. Reaching for it would *lose* the property that the request
   runs as the customer under their own RLS.
4. **Do not pass `userId` into the RPC.** `handlePlaceOrder` uses it only to decide 401; there is
   no `p_user_id` to pass it through.
5. **Never log the request.** Only SQLSTATE + the function's machine code. Validation failures log
   the *path* of the first bad field, never its value. The arguments are the customer's name,
   email, phone and address.
6. **Collapse non-`P0001` SQLSTATEs to a generic 500.** A raw PostgreSQL message names SQL objects.
   Only `P0001` messages are looked up in `BUSINESS_ERRORS`; everything else — including `null` and
   unknown codes — becomes one generic message.
7. **Email recipient is the verified account address**, never `order.customer_email`. Falling back
   would let any account holder relay an order's contents (name, phone, street address) to an
   arbitrary address using your sending domain. `notifyOrderPlaced` skips with
   `no-verified-recipient` instead.
8. **Email failure can never fail an order.** `notifyOrderPlaced` cannot throw; `sendMailgunMessage`
   never throws; bounded by `AbortSignal.timeout(8000)`. A Mailgun `403` still returns `201`.
9. **API key stays in the Authorization header only** — a test asserts the form body does not
   contain it. Failure reasons are short tokens (`http-403`), never Mailgun's response body (which
   echoes the recipient and domain).
10. **`mapPlacedOrder()` validates the function's result**; an unrecognised shape is a failure, not
    a success with `undefined` fields.
11. **`404` not `403` for someone else's order** — avoids an order-existence oracle.
12. **`getDeliveryRegion()` uses a `switch`, not an object lookup** — indexing a plain object with an
    arbitrary string returns whatever is inherited from `Object.prototype`. A test asserts
    `getDeliveryFee("constructor")` is finite.

## 13. Validation and Error Handling

### Validation, layer by layer

| Layer | What it validates | File |
|---|---|---|
| Browser (Zod via RHF) | name 2–80, email, NG phone, address 4–200, city 2–80, state ∈ enum | `lib/checkout/schema.ts` |
| API edge (Zod, `.strict()`) | the same fields **plus** cart 1–50, UUID, int >= 1, no duplicate `productId::size` | `lib/orders/schema.ts` |
| Database (SQL) | text blank/length, 37-state list, JSON array shape, per-key presence+type+regex, dup lines, product exists, size member, stock | `private.place_order` |
| Database (CHECK/ENUM) | non-blank text, `price >= 0`, `quantity > 0`, `total = subtotal + delivery_fee`, `order_status` enum | `20260930215446` |

Duplication is intentional in three places and documented as such: the checkout schema (browser +
API), the state list (Zod + SQL), and the quantity bound (Zod + SQL + CHECK). **A second, looser
server-side schema is the anti-pattern to avoid** — it is how a value ends up accepted in one place
and rejected in the other.

### Error handling patterns

- **API responses:** `{ error: { code, message } }` with customer-written messages only.
  `BUSINESS_ERRORS` in `lib/orders/errors.ts` maps each function code to a status
  (401/400/404/409/500). Everything not `P0001` -> one generic 500.
- **Catalogue queries:** log `error.message` server-side, return `[]` / `null`. Raw PostgREST text
  never reaches the UI.
- **User-facing boundaries:** `app/error.tsx` (route-level, generic copy, shows `error.digest`),
  `app/not-found.tsx`, `components/storefront/empty-state.tsx`.
- **Loading/empty states:** `loading.tsx` for `/auth`, `/shop`, `/shop/[slug]`; skeletons in
  `cart-view.tsx` and `checkout-view.tsx` instead of a `loading.tsx` (see section 19).
- **Client error display:** `role="status"` / `aria-live="polite"` regions rendered **always
  present** so they register before they have content; `CheckoutField` uses `role="alert"` for field
  errors.

## 14. External Services and Integrations

### Supabase (Postgres + Auth + PostgREST)

- **Used for:** all catalogue reads, order reads, the `private.place_order` RPC, and Google OAuth.
- **Where:** `lib/supabase/{client,server,proxy}.ts` — three clients by context
  (browser / server / proxy).
- **Client-side:** `components/auth/google-sign-in-button.tsx` (`signInWithOAuth`),
  `sign-out-button.tsx` (`signOut`).
- **Server-side:** everything in `lib/catalogue`, `lib/orders`, `lib/checkout/profile`,
  `lib/auth/session`.
- **Data sent:** publishable key + session cookies; the RPC sends only the validated order
  arguments.
- **Data received:** catalogue rows; `{order_id, order_number, subtotal, delivery_fee, total}`;
  PostgREST errors (`code`/`message`).
- **Env:** `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`.
- **Failure:** queries log and return empty; RPC errors map to safe messages; auth failures render
  `?error=` copy.

### Google OAuth (via Supabase Auth)

- **Used for:** the only sign-in method.
- **Where:** browser button -> Supabase -> Google -> `/auth/callback`.
- **Data received:** an authorization `code`, exchanged server-side for a session. Scopes: `openid`,
  email, profile.
- **Client-side redirect origin:** derived from `window.location.origin`; the callback origin from
  `request.nextUrl.origin`.
- **Env:** none in the app — the client id/secret live in the Supabase dashboard.
- **Failure:** `?error=access_denied` -> "cancelled"; missing code -> "expired or already used";
  exchange failure -> "couldn't complete".

### Mailgun (transactional email)

- **Used for:** the order-confirmation email (text + HTML).
- **Where:** `app/api/orders/route.ts` -> `notifyOrderPlaced` -> `sendOrderConfirmationEmail` ->
  `sendMailgunMessage`.
- **Side:** **server-only.** Plain `fetch`, no SDK.
- **Data sent:** form-encoded `from` (quoted display name), `to`, `subject`, `text`, `html`; HTTP
  Basic auth `api:<key>` in the `Authorization` header only.
- **Host:** chosen from the domain's region (`api.eu.mailgun.net` for EU domains, otherwise
  `api.mailgun.net`).
- **Env:** `MAILGUN_API_KEY`, `MAILGUN_DOMAIN`, `MAILGUN_FROM_EMAIL` (all required);
  `MAILGUN_FROM_NAME` (optional, defaults to "North & Form").
- **Failure:** `readMailgunConfig()` returns `null` when unconfigured -> `{ok:false,
  reason:"not-configured"}` and the order still succeeds. Timeouts via `AbortSignal.timeout(8000)`.
  **Mailgun free/sandbox domains only send to authorised recipients and answer `403` otherwise** — a
  Mailgun policy, not a bug.

**Not integrated:** no payment gateway, no analytics, no error reporting (no Sentry), no storage
bucket usage in application code.

## 18. Conventions and Patterns

- **TypeScript strict.** No `any`. Where the untyped Supabase client returns `unknown`, rows are
  validated through small `isRecord`/`asString`/`asNumber` helpers at the query boundary rather than
  sprinkling casts.
- **Server Components by default.** `'use client'` only where genuinely needed (cart, forms,
  interactive filters, the mobile menu). A Server Component is passed into a Client Component as
  `children` (`AuthStatus` -> `SiteHeader`) rather than making the client component async.
- **Server-only vs pure is a deliberate axis.** Modules that do I/O import `server-only`; modules
  holding decisions are pure and dependency-injected so they are unit-testable. The comment
  "anything imported by a test cannot be `server-only`" appears repeatedly.
- **One schema, two consumers.** `checkoutSchema` is the single Zod contract for both the browser
  form and the API request.
- **Effects injected into pure decisions.** `handlePlaceOrder({ placeOrder })`,
  `notifyOrderPlaced({ loadOrder, sendEmail })`. This is the project's central testability pattern.
- **Comments explain *why*, and cite the alternative.** Source comments routinely record the bug
  that motivated a line (e.g. why `switch` not object lookup, why `is null` before `jsonb_typeof`,
  why `useState` not a ref). **Read them before changing anything.**
- **Feature-based folders**, not layered. New code joins `lib/<feature>/` + `components/<feature>/`.
- **Database is the catalogue.** Nothing is hardcoded in components; all reads go through
  `lib/catalogue/queries.ts`.
- **Filter/search/sort in Postgres**, never fetch-then-sort.
- **Accessibility is not optional.** `aria-live` regions always rendered, `role="alert"` for field
  errors, `role="status"` sr-only announcements, skip link, `aria-current="page"`, availability
  stated in **words as well as colour**, focus-visible rings throughout.
- **Tailwind utilities over `cn()` for conditional classes**; `cn()` from the standalone `cn`
  package, never a hand-rolled `clsx`+`twMerge`.
- **`formatNaira()` for all money** — `en-NG` locale, `NGN`, zero fraction digits, `tabular-nums` on
  rendered amounts.
- **Long, deliberate comments** are the house style — several files open with a 20–40 line rationale
  block.
- **Names mirror the domain**: `handlePlaceOrder`, `mapPlaceOrderError`, `notifyOrderPlaced`,
  `getAvailability`, `toRpcParams`.

## 19. Important Constraints and Gotchas

**Next.js 16 — this is not the Next.js in your training data.**

1. `middleware.ts` is deprecated -> **`proxy.ts`**, exporting a function named **`proxy`**. Do not
   create `middleware.ts`.
2. **`cookies()` is async** — always `const cookieStore = await cookies()`.
3. **Turbopack is the default** for `next dev` and `next build`.
4. **Generated route types**: `LayoutProps<"/">` in `app/layout.tsx`, `PageProps<"/shop">`,
   `PageProps<"/shop/[slug]">`. Use them; `params`/`searchParams` are awaited.
5. **Error boundaries receive `retry`, not `reset`** (see `app/error.tsx`).
6. Read version-matched docs in `node_modules/next/dist/docs/` before using an API not already used
   here.

**Server/client boundary traps.**

7. **Never add `app/checkout/loading.tsx` or `app/checkout/confirmation/[orderNumber]/loading.tsx`.**
   Verified: a route `loading.tsx` wraps the page in a Suspense boundary that flushes *before* the
   page body runs, which downgrades `requireAuthUser`'s `redirect()` from a `307` to a `200` carrying
   a meta-refresh. The loading state is the **client-side skeleton** in `checkout-view.tsx`, exactly
   as `cart-view.tsx` does it.
8. **Never reuse a server Supabase client across requests.** `lib/supabase/server.ts` imports
   `server-only` to enforce it. Its `setAll` swallows errors because a Server Component cannot write
   cookies.
9. **Never remove the `getClaims()` call in `lib/supabase/proxy.ts`** — it is what triggers the
   refresh, despite the result being discarded.

**Data and order invariants.**

10. **Delivery fees exist twice on purpose**: `getDeliveryFee()` (display) and a `CASE` in
    `private.place_order` (authoritative). Change both together or customers will see a different
    total than they are charged.
11. **The 37-name state list exists twice on purpose**: `lib/checkout/nigeria-states.ts` and the SQL
    array. Keep them in step.
12. **Stock is validated but never decremented.** Two customers can both pass the check for the last
    unit. Changing this requires an explicit payment/order-lifecycle decision, not a side effect of
    checkout.
13. **`total = subtotal + delivery_fee` is a table CHECK.** Adding discounts means relaxing it in a
    migration.
14. **`order_status` is a Postgres enum.** A value added inside a transaction cannot be used by that
    same transaction.
15. **Order history is protected by delete behaviour**: `orders.user_id ON DELETE SET NULL`,
    `order_items.product_id ON DELETE RESTRICT`. "Retire" a product (stock 0, `featured = false`)
    rather than deleting it.
16. **Cart snapshots are never authoritative.** `unitPrice` and `maxQuantity` are add-time UX values;
    checkout must never trust them.
17. **No idempotency key.** Retrying `POST /api/orders` after a network failure creates a second
    order and a second email. This is documented, not a bug to fix casually.
18. **Refreshing the confirmation page sends nothing.** The email trigger is one successful
    `POST /api/orders`, not a page render.
19. **Migrations are append-only.** The four `place_order` migrations are recorded in
    `supabase_migrations.schema_migrations`. Fix a bug with a new migration; never edit a recorded
    one.

## 22. AI Context — Read This First

**What it is.** NORTH & FORM — a fictional Nigerian menswear storefront. Next.js 16 App Router +
React 19 + TS strict + Tailwind v4 + shadcn (Base UI, `base-vega`) + Supabase
(Postgres/Auth/RLS) + Mailgun. Vitest (Node, no DOM). pnpm.

**Core architecture.** RSC pages read Postgres directly through a per-request Supabase server
client. The cart is client-only (React reducer + `localStorage`). **The browser never writes an
order.** `POST /api/orders` -> pure `handlePlaceOrder` -> `private.place_order` (`SECURITY DEFINER`,
`private` schema). `proxy.ts` refreshes the session only — **no route protection there**; protected
pages call `requireAuthUser()` themselves.

**Entities.** `profiles` (1:1 auth.users) - `categories` 1:N -> `products` 1:N -> `order_items` -
`auth.users` 1:N -> `orders` -> `order_items`. Money is `numeric(12,2)`; `orders` enforces
`total = subtotal + delivery_fee`.

**Flows.** Browse (filter/search/sort in Postgres) -> add to bag (`productId::size` lines,
stock-clamped) -> `/checkout` (auth-guarded) -> `POST /api/orders` -> DB prices and creates ->
confirmation page re-reads from DB + email to the **verified** address.

**Security rules (do not weaken).**

- The client sends **only** product ids, quantities, sizes and typed contact/delivery text. Prices,
  totals, status, order number and owner are derived in `place_order` / by RLS.
- `place_order` has **no** `p_user_id`/`p_*_price`/`p_total`/`p_status` parameters — keep it that way.
- **No client INSERT/UPDATE/DELETE policy on `orders`/`order_items`**; **no service-role key in app
  code**.
- `orderRequestSchema` is `.strict()` — a forged key is a 400.
- Only `P0001` maps to a message; every other SQLSTATE -> one generic 500. Never log the request.
- Email recipient = verified account email, never `order.customer_email`.
- `safeRedirectPath()` on every `?next=` use. `getOrderByNumber()` takes **no** user id (RLS is the
  boundary). Unknown-owner -> `404`, never `403`.
- No admin role exists. Don't invent one casually.

**Business rules.** Lagos 2000 / FCT 2500 / Rivers 3000 / other 4000 (duplicated in
`lib/checkout/delivery.ts` **and** in SQL — change both). State must be one of 36 states + FCT
(duplicated in Zod **and** SQL). Status always `awaiting_payment`. **Stock is validated, never
decremented.**

**Where things live.** Catalogue -> `lib/catalogue/{types,queries}.ts`. Cart ->
`lib/cart/{reducer,storage}.ts` + `components/cart/cart-provider.tsx`. Checkout ->
`lib/checkout/*` + `components/checkout/*`. Order API -> `app/api/orders/route.ts` +
`lib/orders/*`. Email -> `lib/email/*`. Auth -> `lib/auth/*` + `proxy.ts`. DB ->

**Conventions.** Strict TS, no `any`; validate rows from `unknown` at the query boundary;

money; accessibility wired deliberately (`aria-live`, `role="alert"`, text-not-colour-only); long

**Hard constraints.** Next 16: `proxy.ts` not `middleware.ts`; `await cookies()`; Turbopack;
`LayoutProps`/`PageProps`; `retry` not `reset`. **Never add `loading.tsx` to `/checkout` or the
